\begin{abstract}
QEMU runs inside Zephyr with device models, the Tiny Code Generator (TCG),
and an Arm EL2 accelerator. The port reuses POSIX threads, clocks, and file
operations. File mappings, positional I/O, signals, and process lifetime
require adapters or restricted behavior. Source inspection, native API
probes, and guest executions identify these limits.

The Zephyr catalog lists 393 interfaces, with qualifications or missing
support labels for 104 entries. A separate audit of 50 host interfaces finds
31 reused APIs, eight adaptations, two metadata limits, and nine unavailable
process or signal extensions. Tests execute Linux, firmware, and static
Linux programs on an outer QEMU platform. The EL2 backend supplies mechanisms
for a Type-1 hypervisor. Physical-board performance, full POSIX conformance,
and production isolation require further evaluation.
\end{abstract}

\noindent\textbf{Keywords:} Zephyr; POSIX compatibility; QEMU porting;
AArch64; TCG; Type-1 hypervisor.

\section{QEMU as a POSIX workload}
\label{sec:introduction}

QEMU combines POSIX services with device models, memory allocation, image
loaders, and generated code~\cite{bellard}. These components depend on file
metadata, descriptor offsets, synchronization, and executable memory. A guest
boot exercises their interactions across the host interface.

Zephyr links applications and kernel code into one image. Its configuration
and C library determine which POSIX services the application can
use~\cite{zephyr-posix}. The port must account for API behavior, resource
limits, and this shared runtime. The evaluation records direct API use,
project adaptations, and missing behavior for the fixed source revisions.

the guest Linux ABI. Each finding records its implementation, configuration,

executed inputs. Figure~\ref{fig:assessment-flow} gives the workflow;

\subsection{The host POSIX interface}

QEMU calls Zephyr and Picolibc for threads, clocks, files, and related host
services. The application enables compiler TLS and sets finite limits for
threads, mutexes, condition variables, and descriptors. These settings are in
\source{apps/qemu_linux/prj.conf} and \source{zephyr/Kconfig}.

\subsection{QEMU library requirements}

QEMU uses the QEMU Object Model (QOM), MemoryRegion, the big QEMU lock (BQL),
and read-copy-update (RCU). The port includes GLib containers and TCG.
The GLib tests record library behavior. Feature exclusions, such as
migration, describe this QEMU build. They require source analysis before
attribution to a missing POSIX service.

\subsection{The guest Linux ABI}

User programs issue Linux AArch64 syscall numbers. Zephyr uses kernel syscall
identifiers generated at build time~\cite{zephyr-implementation}.
\source{src/qemu/ports/zephyr/user-syscall.c} translates the Linux ABI to host
operations. Guest syscall tests examine this adapter and the host services
that it calls.

\section{Porting method}
\label{sec:porting}

\subsection{Build from fixed revisions}

\source{west/west.yml} fixes the QEMU, Zephyr, dtc, and zlib revisions.
The build copies these sources to \source{build/sources/}, applies the patch
series, and adds the port files. \source{zephyr/CMakeLists.txt} selects QEMU
sources and runs the upstream QAPI, trace, and instruction decoder generators.
The build leaves the upstream checkouts unchanged.

The host configuration selects headers and page size definitions. Macro
adapters preserve the different configuration conventions of QEMU and
Zephyr. Aligned allocation uses the C library after size rounding and an
overflow check.

\subsection{Select and verify components}

The system build includes ARM CPUs, QOM/qdev, MemoryRegion, PL011, a software
GICv3, and ARM loaders. The probe in \source{apps/qemu_probe/} constructs QOM
objects and reads and writes PL011 registers.
\source{src/qemu/ports/zephyr/machine.c} defines the guest machine.

The GLib subset supplies the containers and utilities that these sources
use. Differential tests compare its output with host GLib output for the
same inputs. The cases include allocation overflow. The implementation is in
\source{src/qemu/ports/zephyr/glib/}; the tests are in \source{tests/glib/}.
Their results apply to the exercised library behavior.

\subsection{Use one owner thread}

The application starts one POSIX worker with \code{pthread\_create()} and
explicit attributes. This worker owns device operations, CPU execution,
timers, and deferred reclamation. Wrappers call Zephyr pthread functions and
track BQL ownership across execution transitions. The worker invokes deferred
RCU callbacks at quiescent points outside read-side sections.
\source{src/qemu/ports/zephyr/os.c} implements these operations.

The adapters depend on this ownership rule. Positional I/O uses private
descriptors; one-time initialization and RCU operations assume one QEMU owner.
Additional QEMU threads or shared descriptors would require different
synchronization.

\subsection{Load files from Ext2}

Outer QEMU supplies a VirtIO Block disk. Zephyr mounts its Ext2 filesystem
read-only at \source{/images}. The loader reads kernel, initramfs, and ELF
files through \source{src/qemu/ports/zephyr/file.c}. This adapter represents
GLib mapped files as private snapshots and manages their reference counts.

The Ext2 patch permits inode synchronization only on writable mounts.
This preserves the read-only mount during file close and synchronization.

\subsection{Control launch and exit}

System mode creates a machine, selects the compiled accelerator, and loads
the image. A separate user build includes user TCG and the Linux ELF loader.
Shell handlers copy command arguments before they wake the QEMU worker.

The shell directs UART input to a bypass callback during guest execution.
Ctrl-] requests termination; completion restores the prompt. Automatic startup
calls the same handler through \code{shell\_execute\_cmd()}~\cite{shell}.
A worker-local exit target converts QEMU loader exits to command results.
\source{src/qemu/ports/zephyr/console-uart.c} implements the console adapter.

\subsection{Pthreads and time}

Worker attributes select \code{SCHED\_RR} and a supplied memory region.
Mutex and condition wrappers call pthread functions and examine their return
codes. Timed waits use an absolute deadline. The wrapper reads
\code{CLOCK\_REALTIME} through \code{clock\_gettime()}, adds the requested
duration, and normalizes nanoseconds.

Tests exercise worker creation, model locks, and an independent Zephyr thread
during guest execution. Full cancellation, priority, and contention semantics
require separate evaluation. The native probe in
Section~\ref{sec:native-probe} covers condition notification and timeout.

Zephyr timers request execution exits. Halted execution uses wait/kick
synchronization so the QEMU loop can cooperate with the
scheduler~\cite{scheduling}. The recorded runs show host progress; they
supply no worst-case latency bound.

\subsection{Positioned I/O and descriptor semantics}
\label{sec:positioned-io}

Zephyr's \code{pread()} and \code{pwrite()} pass an offset to
\code{zvfs\_rw()}. Its \code{supports\_pread\_pwrite()} check accepts
shared-memory descriptors. These calls return \code{ENOTSUP} for regular-file
descriptors~\cite{device-io,zvfs}.

QEMU's ELF loader requires positional reads from regular files. The adapter
saves the descriptor offset, seeks, does the I/O, and restores the offset.
This sequence assumes one worker owns the descriptor. ELF tests and tests of
private mappings exercise that sequence. Concurrent access through a shared descriptor
requires additional synchronization.

\subsection{File metadata and loader policy}

\code{stat()} returns file type and size. The mode contains
\code{S\_IFREG} or \code{S\_IFDIR}, but no execute-permission
bits~\cite{zephyr-stat}. The ELF loader accepts a regular file
named in the launch command without an execute-bit check. It retains
architecture and address-range validation.

The native probe found mode 0755 in the Ext2 inode and zero permission bits
in the returned metadata. The host API omits permission data that the
filesystem stores.

\subsection{Memory protection and fault delivery}

Host \code{mprotect()} returns \code{ENOSYS}~\cite{zephyr-mprotect}.
User mode disables POSIX mapped files and uses kernel APIs with QEMU page
metadata.

The TCG adapter maps a 16~MiB buffer through distinct writable and executable
aliases with \code{k\_mem\_map\_phys\_bare()}. TCG synchronizes caches before
it executes code through the executable alias.
\source{src/qemu/ports/zephyr/tcg.c} contains the system adapter.

The user runtime reserves a 64~MiB address region. QEMU page metadata controls
its mappings. Checked helpers handle generated loads, stores, atomic
operations, and bulk operations such as DC ZVA. Writes to translated code
invalidate affected translations. Invalid accesses stop the emulated process
with a signal-derived status. Fault tests exercise this behavior in
\source{src/qemu/ports/zephyr/user-memory.c}.

\subsection{Signals, identity and process lifetime}

Zephyr implements signal-set operations. Process-signal functions such as
\code{sigaction()} and \code{kill()} return \code{ENOSYS}~\cite{zephyr-signals}.
The port detects guest faults through memory helpers. It uses
\code{setjmp}/\code{longjmp} for calls with \code{savesigs == 0}.

The user adapter assigns a positive process ID for each launch and a virtual
root identity. Unsupported Linux calls return \code{ENOSYS}. Guest threads
and installed signal handlers lie outside this ABI. Zephyr has pthread and
socket APIs; their availability does not add the corresponding guest
interfaces.

System mode retains its machine and global QEMU state after execution ends.
A new VM requires a Zephyr reboot. User mode closes descriptors and resets
mappings, CPU state, and translation state for each program.

\subsection{Scope of the assessment}

The results apply to the fixed revisions, configured resources, and one
QEMU owner thread. Full POSIX evaluation requires a declared profile and
tests of its complete interface requirements, error paths, and concurrency.

\section{Simulation and virtualization}
\label{sec:capabilities}

\subsection{QEMU machine and TCG execution}

TCG translates guest instructions into host code and reuses translation
blocks associated with CPU state. System emulation uses a software MMU and
device models for MMIO~\cite{tcg}.

The \code{zephyr-virt} machine has one ARM vCPU, a software GICv3, and
256~MiB RAM at \code{0x40000000}. PL011 is at \code{0x09000000}.
The ARM loaders read Linux and ELF images. System TCG runs on an EL1 Zephyr
host. A one-millisecond timer requests execution exits so the owner can
service timers and console I/O.

\subsection{EL2 execution}

Arm EL2 supplies traps and Stage-2 address translation for guest resource
control~\cite{arm-virtualization}. The \code{zephyr} accelerator runs on a
non-VHE EL2 host and calls the \code{zhv} kernel executor. This executor
manages guest transitions, Stage-2 mappings, registers, TLS, SIMD/FP state,
and timers.

The QEMU ARM adapter handles MMIO, system-register, and PSCI exits. It uses
software GICv3 state to deliver interrupts and compares host MIDR fields
with the requested CPU model. The executor is in
\source{src/zephyr/arch/arm64/core/hypervisor/}; the adapter is in
\source{src/qemu/target/arm/zephyr.c}.

These components supply mechanisms for a Type-1 hypervisor on an
application-class SoC. The recorded runs use an outer QEMU \code{virt}
machine with TCG~\cite{virt}. Deployment on hardware requires board support,
memory and interrupt configuration, and tests of the physical virtualization
interface. System accelerators and user mode require separate firmware builds.

\subsection{Linux user execution}

User mode reuses QEMU user TCG and the Linux ELF loader~\cite{qemu-user}.
At \code{svc}, the adapter reads the syscall number from \code{x8} and
arguments from \code{x0} through \code{x5}. It writes the result to \code{x0}.
The implemented calls handle files, private mappings, clocks, entropy, and
selected process metadata.

The installed SDK builds the default static ELF. A regression program adds
file I/O, mapping, and fault cases. These workloads exercise the Linux ABI
adapter and its host services.

An independent observer sleeps for one second between updates. Acceptance
requires observer progress and a maximum gap below the 4000~ms threshold.
A worst-case bound requires analysis of initialization, interrupt masking, allocation,
device operations, and scheduling by outer QEMU.

User tests execute AArch64 instructions and Linux syscalls. They cover private
mappings, self-modifying code, permissions, faults, and successive program
launches. The default hello ELF ran on Ubuntu AArch64. Component results
include 196 filesystem checks, 184 matching GLib output lines, and the
architecture/FPU/executor cases. These counts describe the tests performed.
\source{tests/user/check.py} and \source{tests/user/check_default.py} contain
the user tests.

\subsection{File updates and descriptor lifetime}

\source{scripts/guest_disk.py} fingerprints source contents and replaces a
completed Ext2 image by atomic rename. Outer QEMU holds the attached disk
for its session. A Zephyr reboot resets the inner runtime and retains that
disk attachment.

The update experiment replaced hello with the Linux ABI regression program
at the same path, then regenerated the disk. The existing session continued
to run hello after a Zephyr reboot. A new outer QEMU process ran the
replacement and returned its expected status 7. Updated disk contents
require a restart of outer QEMU.

\section{Limits and deployment}
\label{sec:implications}

The port needs adapters for positional I/O, incomplete metadata, executable
memory, signals, and process lifetime. Evaluation must identify which behavior
comes from Zephyr POSIX, the C library, a kernel API, or project code.
Normal results, error paths, and concurrency each require tests.

System mode permits one VM and one vCPU per Zephyr boot. User mode permits
one static, single-threaded program at a time. The profile excludes migration,
hotplug, guest EL2/EL3, general signal delivery, dynamic linking, and guest
process creation.

Tests use an emulated Arm platform. The record contains no physical-board
measurements of throughput, interrupt latency, energy, or memory bandwidth.
Fault tests cover selected cases; image parsers and device models still run
inside the Zephyr application. Production isolation and real-time bounds
require separate evaluation. A physical SoC also needs a BSP and configured
memory, GIC, timer, and exception levels.

\section{Reproduction}
\label{sec:artifact}

The repository contains fixed upstream revisions, patches, host and executor
code, samples, and acceptance scripts~\cite{project}. Builds require Linux
x86\_64/AArch64 or macOS Apple Silicon and Python 3.12 or newer.
Check out the revision in Section~\ref{sec:evaluation}. Then run:

\begin{quote}
\begin{minipage}{\linewidth}
\small\ttfamily
bash scripts/install-host-deps.sh\\
make setup\\
make doctor\\
make check ACCEL=zephyr CPU=cortex-a53\\
make check QEMU\_SHELL=1 ACCEL=tcg\\
make check-firmware\\
make check-firmware ACCEL=tcg\\
make check-user\\
make probe test-payload test-glib\\
make test-tools\\
make test-arch
\end{minipage}
\end{quote}

Use the documented A57 and A72 selections for those CPU models. Record the
repository revision, tool versions, configuration, and console output.
The build uses Python requirements from the fixed Zephyr revision.
These files do not lock the complete dependency tree.

\source{docs/guidelines.md} and \source{docs/guidelines.zh-CN.md} give
instructions for installation, file updates, and restarts. Section~\ref{sec:assessment}
cites the source implementations. The reference and validation records have
an access date of 9 October 2026.

Docutils extracts the upstream tables. The generated catalog retains support
cells, exclusions, duplicate occurrences, and source hashes. The host audit
has its own versioned CSV. \source{scripts/posix_figures.py} regenerates the
inventories and Matplotlib plots with \source{docs/requirements-figures.txt}.

The flow source is \source{docs/figures/posix-porting-flow.mmd}. This manuscript
contains the vector graphics and chart values. Figure preparation uses the
Scientific Visualization workflow~\cite{scientific-skills}.
